`connectors/mysql/sink` (registered as `mysql`, **alpha**, though the MySQL
source is beta) loads each resource into its own typed MySQL table with native
column types, primary keys, and `NOT NULL` constraints from the source schema.
It requires MySQL 8.0 or newer, since batch inserts are expanded server-side
with `JSON_TABLE`.

## Configuration

| Field | Scope | Default | Description |
| --- | --- | --- | --- |
| `connection_method` | Connection | `fields` | `fields` builds the DSN from the fields below. `url` uses `dsn` directly. |
| `dsn` | Connection | — | MySQL URL or driver DSN. Required when `connection_method` is `url`. Secret. |
| `host` | Connection | — | Server hostname. Required in `fields` mode. |
| `port` | Connection | `3306` | Server port |
| `username` | Connection | — | Required in `fields` mode |
| `password` | Connection | — | Required in `fields` mode. Secret. |
| `database_name` | Connection | — | Database to connect to. Required in `fields` mode. |
| `tls_mode` | Connection | `preferred` | `false`, `preferred`, `true`, or `skip-verify` |
| `database` | Pipeline | — | Destination database. Falls back to the database in the DSN. |
| `mode` | Pipeline | `typed` | Destination table mode. `typed` is the only value. |

It is an error for both `database` and the DSN database to be empty. Left
empty server-side, `database` defaults to the normalized source connection
name.

`Open` runs `CREATE DATABASE IF NOT EXISTS` for the destination through a
bootstrap connection, then sizes the pool to at least 4 connections (or the
run's snapshot parallelism, whichever is larger). `TestConnection` clears the
database name first, so a destination database that does not exist yet still
validates. The sink prefers batches of 4,096 rows.

## Supported write modes

The sink advertises `full_replace`, `full_append`, `full_upsert`,
`incremental_upsert`, and `cdc`. See
[replication modes](/pages/guides/concepts/replication-modes). They bind to
three behaviors:

- `full_replace` and `full_append` insert plainly. Both are full-snapshot
  policies, so the destination table is truncated before each run (see below).
- `full_upsert` and `incremental_upsert` insert with
  `ON DUPLICATE KEY UPDATE`, making re-runs and retries idempotent.
- `cdc` merges changes in arrival order. Inserts and updates upsert, and
  deletes delete.

## Table management

Before extraction, `EnsureSchema` runs per resource:

1. `CREATE TABLE IF NOT EXISTS` with typed columns and a primary key.
2. `TRUNCATE` — unless the bound write mode is upsert or merge. This applies to
   every non-upsert policy, **including `full_append`**. A full-snapshot append
   run starts from an empty table.
3. Missing columns are added by checking `information_schema.columns` and
   issuing `ALTER TABLE … ADD COLUMN` for each absent one (MySQL has no
   `ADD COLUMN IF NOT EXISTS`). Evolution is add-only. Incompatible type
   changes are not applied and surface as cast errors during writes.

### Type mapping

| Logical type | MySQL type |
| --- | --- |
| `bool` | `tinyint(1)` |
| `int16` / `int32` / `int64` | `smallint` / `int` / `bigint` |
| `float32` / `float64` | `float` / `double` |
| `decimal` | source-native type if the source is MySQL, else `decimal(38,9)` |
| `string` | source-native type if the source is MySQL, else `longtext` |
| `bytes` | `longblob` |
| `date` / `time` | `date` / `time(6)` |
| `timestamp` | `datetime(6)` |
| `timestamptz` | `datetime(6)`, normalized to UTC |
| `json` / `array` | `json` |
| `uuid` | `char(36)` |

`timestamptz` maps to `datetime(6)` rather than MySQL's `timestamp` because
`timestamp` cannot represent values past 2038. Native types from other engines
are ignored. Only MySQL-native declarations pass through.

## Write mechanics and atomicity

Each batch is serialized to one JSON array parameter and expanded server-side:

```sql
INSERT INTO db.tbl (...)
SELECT ... FROM JSON_TABLE(?, '$[*]' COLUMNS(...)) AS r
```

Bytes columns are decoded with `FROM_BASE64`. Upserts append
`ON DUPLICATE KEY UPDATE`. Because MySQL reports 2 affected rows per updated
row, the receipt reports `min(len(records), RowsAffected)`.

CDC batches are split into runs of consecutive deletes and non-deletes, applied
in arrival order in **one transaction per batch**. Deletes use a multi-table
`DELETE` joined against `JSON_TABLE`.

Non-CDC batches commit as they are applied, so partial data is visible mid-run.
Delivery is at-least-once, and upsert and merge modes converge through the
primary key.

## Failure behavior

On a failed run, `Abort` **truncates every non-resumable table the run
ensured**. A failed `full_replace` or `full_append` run leaves the destination
tables it touched empty. Tables bound to upsert or merge modes (`full_upsert`,
`incremental_upsert`, `cdc`) are preserved, since a retry converges through the
primary key.
