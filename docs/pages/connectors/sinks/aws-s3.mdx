Connector ID `s3`

The Amazon S3 sink writes each resource as one NDJSON, JSON, or
Parquet object per finite write in an S3-compatible bucket, laid out so an external
table per resource can read it directly. It is not a lakehouse format with
table-level atomic commits. See the Iceberg sink for that.

## Configuration

| Field | Scope | Default | Description |
| --- | --- | --- | --- |
| `bucket` | Connection | — | Required. Destination S3 bucket. |
| `region` | Connection | SDK default | AWS region |
| `endpoint` | Connection | AWS | Custom S3 endpoint (e.g. MinIO) |
| `path_style` | Connection | `true` for custom endpoints | Use path-style bucket addressing |
| `auth_method` | Connection | `instance_profile` | `instance_profile` or `iam_credentials` |
| `access_key_id` | Connection | — | Required for IAM Credentials. Secret. |
| `secret_access_key` | Connection | — | Required for IAM Credentials. Secret. |
| `session_token` | Connection | — | Optional for temporary IAM Credentials. Secret. |
| `prefix` | Pipeline | — | Root folder for the pipeline, surrounding `/` trimmed |
| `partition` | Pipeline | `dt={{.Date}}` | Folders between each resource and its files; see [partition template](#partition-template) |
| `file_format` | Pipeline | `ndjson` | `ndjson`, `jsonl`, `json`, or `parquet`; see [file formats](#file-formats) |
| `compression` | Pipeline | per format | `none` or `gzip` for JSON formats; `snappy` for Parquet |
| `part_size_mib` | Pipeline | `16` | Starting multipart request size in MiB, from 5 through 5120. Parts double in size every 1,000 parts, so any value reaches the 5 TiB S3 object limit within 10,000 parts |
| `max_file_size_mib` | Pipeline | `1024` | Target object size in MiB, from 5 through 1048576. A resource that grows past it continues in the next numbered object |
| `upload_concurrency` | Pipeline | `4` | Concurrent S3 upload operations across resources, from 1 through 32 |

A `prefix` left empty is defaulted server-side to the normalized source
connection name.

**Instance Profile** is the default. It uses the AWS SDK default credential
chain, including EC2 instance profiles and container or workload roles. Choose
**IAM Credentials** to provide `access_key_id` and `secret_access_key`; add
`session_token` when using temporary credentials.

`TestConnection` performs a read-only `HeadBucket` request. On AWS this
requires `s3:ListBucket`; it does not prove that the identity can write. Runs
also need object-write and multipart-upload permissions for the configured
prefix.

## Supported write modes

The sink advertises `full_replace` and `full_append`. See
[replication modes](/pages/guides/concepts/replication-modes). Because every
run writes its own objects, **the two modes behave identically here**. Each
run produces a fresh object per resource and never touches a previous run's
objects. A full replace run is therefore a snapshot in its own date partition.
Query the latest partition to read the current state, or every partition to
read history.

## Object layout

Each successful bounded run writes one or more numbered objects per resource
and a success manifest. With prefix `local_pg`, resources `accounts` and
`orders`, and the default partition, a bounded run where `orders` outgrew
`max_file_size_mib` has this layout.

```
local_pg/accounts/dt=2026-09-10/cc7332f3-7abc-5f37-984d-9815634f1d7f.0000.parquet
local_pg/orders/dt=2026-09-10/cc7332f3-7abc-5f37-984d-9815634f1d7f.0000.parquet
local_pg/orders/dt=2026-09-10/cc7332f3-7abc-5f37-984d-9815634f1d7f.0001.parquet
local_pg/_runs/cc7332f3-7abc-5f37-984d-9815634f1d7f/_SUCCESS.json
```

The bounded path contains the prefix, resource, partition folders, run ID, and
a four-digit file number that starts at `0000`. Every object is a complete file
in its format, with its own gzip trailer, JSON array, or Parquet footer, so
readers can process the files of one resource in parallel.
Continuous append uses a fresh write identity for every boundary while retaining
the logical run ID in the manifest. A continuous boundary has this layout.

```text
local_pg/accounts/dt=2026-09-10/<write-id>.0000.parquet
local_pg/orders/dt=2026-09-10/<write-id>.0000.parquet
local_pg/_runs/<run-id>/<write-id>/_SUCCESS.json
```

Resource objects remain grouped by resource, so an external table can point at
`local_pg/accounts/`. Manifests live under `_runs`, which query engines usually
skip. Continuous replace is not supported. Each append boundary reopens the
sink and produces independent objects and a manifest.

### Partition template

`partition` sets the folders between each resource and its files. Write it as
a path with placeholders in double braces. Time placeholders use
the bounded run's start time or the continuous write's start time in UTC.
Every object in that finite write uses the same time. The logical run ID in
`{{.Run}}` stays unchanged across continuous boundaries.

| Placeholder | Value |
| --- | --- |
| `{{.Date}}` | Run or continuous write start date as `YYYY-MM-DD` |
| `{{.StartedAt}}` | Run or continuous write start as a UTC time. Append `.Format "layout"` to shape it |
| `{{.Resource}}` | Resource name |
| `{{.Run}}` | Run identifier |

The default `dt={{.Date}}` is a Hive-style partition that Athena, Glue
crawlers, Spark, and DuckDB discover without extra configuration. Other
layouts:

| Template | Result |
| --- | --- |
| `dt={{.Date}}` | `accounts/dt=2026-09-10/<run>.0000.parquet` |
| `month={{.StartedAt.Format "2006-01"}}` | `accounts/month=2026-09/<run>.0000.parquet` |
| `year={{.StartedAt.Format "2006"}}/month={{.StartedAt.Format "01"}}` | `accounts/year=2026/month=09/<run>.0000.parquet` |
| `{{.StartedAt.Format "2006/01/02"}}` | `accounts/2026/09/10/<run>.0000.parquet` |
| empty | `accounts/<run>.0000.parquet` |

`Format` takes a [Go time layout](https://pkg.go.dev/time#pkg-constants),
where `2006`, `01`, `02`, and `15` stand for year, month, day, and hour. Plain
directories without `key=value` names need Athena partition projection with a
location template.

The template is checked when the pipeline is saved. It must produce a relative
path with no empty, `.`, or `..` segments, and unknown placeholders are
rejected. Helm charts that render pipeline YAML treat `{{` as their own
syntax, so escape the template there as `{{ "{{" }}.Date{{ "}}" }}`.

### File formats

`file_format` chooses how each resource object is encoded. The extension and
`Content-Type` follow the format, and gzip adds a `.gz` suffix and
`Content-Encoding: gzip`.

| Format | Extension | Content-Type | Compression | Layout |
| --- | --- | --- | --- | --- |
| `ndjson` | `.ndjson` | `application/x-ndjson` | `none` (default), `gzip` | One JSON object per line |
| `jsonl` | `.jsonl` | `application/x-ndjson` | `none` (default), `gzip` | One JSON object per line |
| `json` | `.json` | `application/json` | `none` (default), `gzip` | One JSON array of objects |
| `parquet` | `.parquet` | `application/vnd.apache.parquet` | `snappy` | Typed columns from the source schema |

JSON formats write source field names and JSON-compatible values:

```json
{"id":1,"name":"Ada"}
```

Parquet writes typed columns from the resource schema. Parquet is the format
to choose when the bucket is queried by Athena, Spark, or DuckDB.
The `compression` field shows only the options valid for the selected format.

Parquet combines source batches into row groups of up to 65,536 rows instead
of creating a group for every source transaction. Groups also rotate at an
8 MiB target for page data, checked between nonempty batches. A batch and
pending page buffers can exceed this target. The last group is flushed at
commit.

The success manifest lists every resource with its total rows and bytes and the
key, URI, rows, bytes, and CRC32C of each of its objects, in file order.
Programmatic consumers should treat `_SUCCESS.json` as the visibility boundary
and ignore writes without it.

```json
{
  "version": 2,
  "run": "cc7332f3-7abc-5f37-984d-9815634f1d7f",
  "resources": [
    {
      "name": "orders",
      "rows": 2400000,
      "bytes": 1610612736,
      "files": [
        {
          "key": "local_pg/orders/dt=2026-09-10/cc7332f3-7abc-5f37-984d-9815634f1d7f.0000.parquet",
          "uri": "s3://bucket/local_pg/orders/dt=2026-09-10/cc7332f3-7abc-5f37-984d-9815634f1d7f.0000.parquet",
          "rows": 1600000,
          "bytes": 1073807360,
          "crc32c": "8f2a61c4"
        },
        {
          "key": "local_pg/orders/dt=2026-09-10/cc7332f3-7abc-5f37-984d-9815634f1d7f.0001.parquet",
          "uri": "s3://bucket/local_pg/orders/dt=2026-09-10/cc7332f3-7abc-5f37-984d-9815634f1d7f.0001.parquet",
          "rows": 800000,
          "bytes": 536805376,
          "crc32c": "17c0be3a"
        }
      ]
    }
  ]
}
```

Version 1 manifests had one `key`, `uri`, and `crc32c` per resource. Version 2
moves them into `files` because a resource can span several objects.

S3 verifies every manifest checksum. Each part is sent with its CRC32C, each
multipart object is completed with a full-object CRC32C, and each single object
is uploaded with its CRC32C. S3 rejects any write whose stored bytes do not
match, and the run fails before `_SUCCESS.json` is published. The CRC32C S3
reports for an object therefore equals the manifest value. An S3-compatible
endpoint must support CRC32C full-object checksums, which MinIO does. Query engines cannot apply that rule and
read every object under the table location. See failure behavior below.

## Write mechanics and atomicity

The sink streams full part buffers as multipart uploads while the run is active.
The first 1,000 parts of an object are `part_size_mib` each, and the part size
doubles every 1,000 parts after that, up to 5 GiB. Object size is unknown while
it streams, and growing the parts keeps large objects within the 10,000-part S3
limit without large buffers for small objects.

When an object reaches `max_file_size_mib`, the sink closes it at the next batch
boundary and continues in the next numbered object. Objects can exceed the
target by up to one encoded batch, and Parquet objects by up to one row group.
A closed object uploads its last part right away, so its memory is released,
but its multipart upload stays open until `Commit`. Rolled objects are
therefore no more visible than any other object before `Commit`, and `Abort`
removes them. `upload_concurrency` limits S3 requests across resources; when
that limit is reached, source extraction waits. At commit, Filament uploads the
remaining bytes and completes each object. Small resources use `PutObject`.

A selected resource with no rows produces no object and does not appear in
`_SUCCESS.json`. This keeps continuous runs from leaving an empty object for
every quiet resource at every boundary.

The sink does not need temporary disk for the full run. Memory use comes mainly
from unfinished multipart buffers, in-flight uploads, and the current encoded
batch. Each of those buffers is at most one part, so peak memory grows as a
very large object moves into larger parts. Parquet also buffers one row group
per active resource. Objects smaller than one part remain in memory until commit.

Each resource object is atomic, but a group of S3 objects cannot be committed
atomically. Resource objects may be visible while `Commit` is still running.
The write becomes valid only when `_SUCCESS.json` is uploaded last.

## Failure behavior

`Abort` cancels in-flight work and abandons incomplete multipart uploads. If
`Commit` fails after some resources complete, those objects remain in their
resource partitions, but no `_SUCCESS.json` is published, so the write is not
valid. Query engines still read those objects. If partial data matters, remove
them by their run ID for bounded output or write ID for continuous output
before retrying. Configure an S3 lifecycle
rule to expire incomplete multipart uploads. Multipart uploads do not resume across worker
attempts. Resource progress is saved only after commit succeeds.

See [Continuous streaming runs](/pages/guides/concepts/streaming) for boundary
defaults, setup costs, and checkpoint recovery. A replay after publication can
produce another append object with the same rows under a new write identity.
