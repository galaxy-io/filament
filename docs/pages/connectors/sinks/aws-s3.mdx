The Amazon S3 sink (**alpha**) writes each resource as one NDJSON object in an
S3-compatible bucket, using the same row format as
[stdout](/pages/connectors/sinks/standard-output). It is an uncompressed JSON
export, not a partitioned Parquet or lakehouse format.

## Configuration

| Field | Scope | Default | Description |
| --- | --- | --- | --- |
| `bucket` | Connection | — | Required. Destination S3 bucket. |
| `region` | Connection | SDK default | AWS region |
| `endpoint` | Connection | AWS | Custom S3 endpoint (e.g. MinIO) |
| `path_style` | Connection | `true` for custom endpoints | Use path-style bucket addressing |
| `auth_method` | Connection | `instance_profile` | `instance_profile` or `iam_credentials` |
| `access_key_id` | Connection | — | Required for IAM Credentials. Secret. |
| `secret_access_key` | Connection | — | Required for IAM Credentials. Secret. |
| `session_token` | Connection | — | Optional for temporary IAM Credentials. Secret. |
| `prefix` | Pipeline | — | Key prefix, surrounding `/` trimmed |
| `part_size_mib` | Pipeline | `16` | Multipart request size in MiB, from 5 through 5120; with the 10,000-part limit, the default supports objects up to about 156 GiB |
| `upload_concurrency` | Pipeline | `4` | Concurrent S3 upload operations across resources, from 1 through 32 |

A `prefix` left empty is defaulted server-side to the normalized source
connection name.

**Instance Profile** is the default. It uses the AWS SDK default credential
chain, including EC2 instance profiles and container or workload roles. Choose
**IAM Credentials** to provide `access_key_id` and `secret_access_key`; add
`session_token` when using temporary credentials.

`TestConnection` performs a read-only `HeadBucket` request. On AWS this
requires `s3:ListBucket`; it does not prove that the identity can write. Runs
also need object-write and multipart-upload permissions for the configured
prefix.

## Supported write modes

The sink advertises `full_replace` and `full_append`. See
[replication modes](/pages/guides/concepts/replication-modes). Because every
run writes to run-scoped keys, **the two modes behave identically here**. Each
run produces a fresh object set and never touches a previous run's objects.
There is no stable "current" object per resource, so downstream consumers must
list runs (or track run IDs) to find the latest.

## Object layout

Each successful run contains one object per resource and a success manifest:

```
<prefix>/<run>/<resource>.ndjson
<prefix>/<run>/_SUCCESS.json
```

with `Content-Type: application/x-ndjson`. Each line is one source row, using
the source field names and JSON-compatible values:

```json
{"id":1,"name":"Ada"}
```

There is no table management or schema section here. The sink is not
schematized and writes the Arrow batch rows as JSON objects.

The success manifest lists every resource's key, URI, rows, bytes, and object
CRC32C. Consumers must treat `_SUCCESS.json` as the visibility boundary and
ignore run prefixes without it.

## Write mechanics and atomicity

The sink streams full `part_size_mib` buffers as multipart uploads while the run
is active. `upload_concurrency` limits S3 requests across resources; when that
limit is reached, source extraction waits. At commit, Filament uploads the
remaining bytes and completes each object. Small resources use `PutObject`, and
a selected resource with no rows becomes a zero-byte object.

The sink does not need temporary disk for the full run. Memory use comes mainly
from unfinished multipart buffers, in-flight uploads, and the current encoded
batch. Objects smaller than one part remain in memory until commit.

Each resource object is atomic, but a group of S3 objects cannot be committed
atomically. Resource objects may be visible while `Commit` is still running;
the run becomes valid only when `_SUCCESS.json` is uploaded last.

## Failure behavior

`Abort` cancels in-flight work and abandons incomplete multipart uploads. If
`Commit` fails after some resources complete, those objects may remain under
the run prefix, but no `_SUCCESS.json` is published, so the prefix is not a
valid run. Configure an S3 lifecycle rule to expire abandoned run prefixes and
incomplete multipart uploads. Multipart uploads do not resume across worker
attempts; resource progress is saved only after commit succeeds.
