HubSpot is a manifest-driven source — `connectors/http/manifests/hubspot.yaml`
declares its resources, auth, and pagination against the shared grammar in
`connectors/http/manifest/`; no HubSpot-specific Go code exists. See
[HTTP](/pages/connectors/sources/http) for how the manifest mechanism works.

## Auth

A private app access token (`pat-na1-…`), created under **Settings →
Integrations → Private Apps**. It is sent as `Authorization: Bearer <token>`.

HubSpot's other credential path, the public-app OAuth flow, is
authorization-code with refresh tokens, which grammar v1 does not model — only
client-credentials OAuth is supported. Private apps are the supported route
here, and they are the mechanism HubSpot itself recommends for single-portal
integrations.

Grant the private app read scopes for every stream you enable. A token missing
a scope gets `403` on that resource, and a failed resource fails the run.

### Property selection

HubSpot's list endpoints return only three properties per record
(`hs_object_id`, `hs_createdate`, `hs_lastmodifieddate`) unless the request
names the ones it wants, and there is no wildcard. The connector therefore
ships ten property-selector settings, each defaulting to a curated list of
HubSpot's standard properties for that family of objects:

| Setting | Applies to |
|---|---|
| `contact_properties` | `contacts` |
| `company_properties` | `companies` |
| `deal_properties` | `deals` |
| `ticket_properties` | `tickets` |
| `lead_properties` | `leads` |
| `engagement_properties` | `calls`, `emails`, `meetings`, `notes`, `tasks`, `communications`, `postal_mail` |
| `product_properties` | `products`, `line_items` |
| `quote_properties` | `quotes` |
| `commerce_properties` | `carts`, `orders`, `invoices`, `commerce_payments`, `subscriptions`, `discounts`, `fees`, `taxes` |
| `object_properties` | `feedback_submissions`, `goal_targets`, `appointments`, `courses`, `listings`, `services` |

Custom properties are portal-specific, so the defaults cannot know about
yours — append their internal names to the relevant setting. HubSpot documents
that "if any of the specified properties are not present on the requested
object(s), they will be ignored", so over-listing is safe and is why one
setting can cover several object types at once.

## Resources

Seventy-two resources, all statically discovered. Five fan out from a parent;
the rest are top-level lists.

### Pagination

Nearly every HubSpot collection returns `{"results": [...], "paging": {"next":
{"after": "…"}}}` and takes the cursor back as `?after=`. The manifest declares
that once in `defaults:`, so a resource only mentions pagination when it
differs. HubSpot drops the whole `paging` object on the final page, which the
cursor paginator treats as termination.

Three shapes deviate:

- `lists` is `POST /crm/v3/lists/search` and pages by mutating the request
  body — `offset` and `count` — with HubSpot's documented maximum of 500 per
  page.
- Definition endpoints (`properties`, `pipelines`, `schemas`, `teams`,
  `roles`, `subscription_definitions`) return the whole collection in one
  `results` array with no `paging` at all; they are declared
  `pagination: none`.
- `account_details` returns a bare object rather than a collection, so it is
  `cardinality: one` with the record at the response root.

CRM object lists request `limit=100`, HubSpot's per-page maximum.
`list_memberships` requests 250, its own documented maximum. Every other list
requests 100 except `forms`, which is held at 50.

### Quirks

- **API version.** The manifest targets the stable `v3`/`v4` paths rather than
  HubSpot's newer date-based versions (`/crm/objects/2026-03/…`). The dated
  versions carry an 18-month end-of-life by design; `v3` has no announced
  sunset and covers the whole surface, including the CMS, files, settings, and
  conversations APIs that the dated scheme has not fully absorbed.
- **Properties are a map, not columns.** `properties` is emitted as a single
  JSON column rather than being flattened. HubSpot property sets differ per
  portal, so flattened columns would not be a stable schema across accounts;
  unnest downstream using `*_property_definitions`.
- **Associations are ids, not rows.** The `associations` query parameter
  returns associated record ids inline, capped by HubSpot at 100 per record
  per type. Records with more associations than that are truncated in the
  `associations` column; use the association APIs directly if you need the
  complete edge list for a hub record.
- **CMS records use `created`/`updated`,** not `createdAt`/`updatedAt`. The
  field names in those streams follow the API rather than being normalised.
- **Rate limiting is capped at 8 requests/second.** Private apps get 100
  requests per 10 seconds on Free and Starter, 190 on Professional and
  Enterprise. 8 rps with the limiter's 2× burst stays inside the lowest tier's
  window (16 + 80 &lt; 100), so the connector is safe on every plan without a
  per-plan setting. HubSpot's rate-limit headers report an interval in
  milliseconds with no reset timestamp, which the dynamic limiter cannot use,
  so the ceiling is static.
- **The `for_each` resources issue one request per parent record.**
  `conversation_messages` and `list_memberships` dominate a run on a busy
  portal — one request per thread and per list respectively, each then paged.
  Disable them if you only need thread- and list-level rows.

## Modes

`ModeFull` and `ModeIncremental` (see [HTTP](/pages/connectors/sources/http)).

Ten resources declare an `incremental:` block, each replaying its watermark
into the since-parameter the endpoint actually documents, with a `time`
comparator and a 60-second overlap so retroactive edits at the boundary are
re-read:

| Resource | Cursor field | Request parameter |
|---|---|---|
| `marketing_emails` | `updatedAt` | `updatedAfter` |
| `blog_posts` | `updated` | `updatedAfter` |
| `blog_authors` | `updated` | `updatedAfter` |
| `blog_tags` | `updated` | `updatedAfter` |
| `site_pages` | `updated` | `updatedAfter` |
| `landing_pages` | `updated` | `updatedAfter` |
| `url_redirects` | `updated` | `updatedAfter` |
| `files` | `updatedAt` | `updatedAtGte` |
| `conversation_threads` | `latestMessageTimestamp` | `latestMessageTimestampAfter` |
| `audit_logs` | `occurredAt` | `occurredAfter` |

Everything else — including every CRM object — is a full extract on every run,
and that is a property of the API, not a shortcut. `GET /crm/v3/objects/{type}`
accepts no filter of any kind: no `updatedAfter`, no `since`, no sort. Declaring
an incremental block against it would checkpoint a watermark that the endpoint
silently ignores while still re-reading everything.

HubSpot's filterable alternative is `POST /crm/v3/objects/{type}/search`, which
does support `hs_lastmodifieddate GTE`, but it returns at most 10,000 results
for any one query and is rate-limited separately at 5 requests/second. A first
run against a portal with more than 10,000 records of a type would hit that
ceiling, so the search endpoint is not used. If full extracts of `contacts` or
`emails` become too expensive, narrow the property lists first — payload size,
not request count, is what makes those runs slow.
