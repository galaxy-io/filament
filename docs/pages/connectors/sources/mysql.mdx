The MySQL source reads from MySQL 8.0+ in two modes, resumable keyset
snapshots and binlog CDC. There is no incremental mode. Full and CDC are the
only options today. The connector is beta.

## Snapshot reads

InnoDB clusters rows by primary key, so key order is physical order. Every
table with a primary key reads via keyset (`WHERE pk > cursor ORDER BY pk
LIMIT page_size`), and each page is a sequential range scan of the clustered
index. There is no separate physical-scan tier as on PostgreSQL.

Large tables split into primary-key range shards, sized from
`information_schema.TABLES.DATA_LENGTH` divided by the InnoDB page size and
the configured `shard_pages`, capped at 64 shards. An integer leading key
splits arithmetically over `MIN`/`MAX`, while anything else (UUID, varchar,
datetime) gets equal-count boundaries sampled via a single `ROW_NUMBER()`
scan. Cursor predicates are written as a disjunctive expansion
(`a > ? OR (a = ? AND b > ?)`) because MySQL's range optimizer cannot use a
row-constructor comparison for an index seek.

Each shard runs in its own `REPEATABLE READ` transaction opened `WITH
CONSISTENT SNAPSHOT, READ ONLY`. These are per-shard snapshots, not one
shared snapshot across the run. Unlike the PostgreSQL source, parallel
shards may observe the table at slightly different moments. Rows are read
through the driver's text protocol and parsed directly into Arrow-backed row
writers; binary columns remain raw bytes.

A table without a primary key is read in a single streaming pass with a
synthetic `ROW_NUMBER()` id. That pass is not resumable, so a resume re-reads
the whole table.

## CDC

CDC connects as a binlog replica (go-mysql `BinlogSyncer`) and decodes
insert, update, and delete events into the same row shape the snapshot
reader produces. Runs have catch-up semantics. Each captures the server's
current binlog position as a watermark, streams from the checkpoint up to it,
and returns. Continuous CDC is a re-request loop, so it can run on a schedule.
No-change runs still persist the watermark.

The cursor is a **GTID set** when the server runs `gtid_mode=ON` (preferred,
since a GTID set survives replica promotion), falling back to **file:pos**
otherwise. An existing file:pos checkpoint keeps that cursor kind even if the
server later enables GTIDs. GTID checkpoints record the last committed
transaction. A crash mid-transaction replays the whole transaction, which the
sink's idempotent merge absorbs.

<Warning>
  MySQL CDC does not snapshot existing rows. The first run starts at the
  current binlog tail, so rows present before the pipeline was created are
  never emitted by CDC. To backfill, run a full pipeline against the same
  tables first, then switch to CDC.
</Warning>

Requirements:

- `ROW` binlog format (the 8.0+ default)
- Binlog retention covering the resume window
- `REPLICATION SLAVE` and `REPLICATION CLIENT` privileges
- A TCP connection (unix sockets are rejected for CDC)

Behavior worth knowing:

- A primary-key-changing update is emitted as a delete of the old row plus an
  insert of the new one.
- Column names are not in the binlog. Each table's column list is read from
  `information_schema` (this works with `binlog_row_metadata=MINIMAL`) and
  the cache is invalidated on any DDL event.
- A column-count mismatch between a binlog event and the cached schema fails
  the run rather than mis-mapping values. Re-snapshot the table after
  incompatible DDL.

See [Replication modes](/pages/guides/concepts/replication-modes) for how
modes map to write policies.
