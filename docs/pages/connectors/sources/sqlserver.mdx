Connector ID `sqlserver`

The SQL Server source reads from self-managed SQL Server 2017 and later, on
premises or on a VM, with resumable keyset snapshots and incremental watermark
reads. It is in preview.

For Azure SQL Database and Azure SQL Managed Instance use the
[Azure SQL source](/pages/connectors/sources/azuresql). It runs the same reader
with connection settings for Azure and Microsoft Entra sign-in.

## Snapshot reads

Tables with a primary key are read in key order. SQL Server stores a table in
its clustered index, which is normally the primary key, so each read is a
sequential range scan. Filament saves the last key each shard delivered, so an
interrupted read resumes where it stopped.

A table larger than `shard_rows` splits into as many as 64 ranges over its
leading key column, each read on its own connection by one streaming query.
Integer keys split by arithmetic over the key range. Other keys split at
sampled boundaries with roughly equal row counts. Composite keys are
supported.

Each range reads inside its own transaction. Under snapshot isolation a range
sees one point in time without taking shared locks, but parallel ranges may
see the table at slightly different moments, because SQL Server cannot share a
snapshot between sessions. Enable snapshot isolation on the source database
for consistent, non-blocking reads.

```sql
ALTER DATABASE app SET ALLOW_SNAPSHOT_ISOLATION ON;
```

A table without a primary key is read in a single streaming pass. That pass is
not resumable, so a resume re-reads the whole table. A table whose primary key
includes a `sql_variant` column is read the same way, because a saved key of
that type cannot be compared reliably on resume.

| `binary`, `varbinary`, `image`, `rowversion` | bytes |

| `hierarchyid` | string, the path form such as `/1/2/` |
| `geometry`, `geography` | bytes in well-known binary, with Z and M |
| `json` | json |
| `sql_variant`, `vector` | string |

Times and timestamps carry microseconds, so the 100 ns digit of a `time(7)`,
`datetime2(7)` or `datetimeoffset(7)` value is truncated. `datetime2` is scale
7 unless declared otherwise. In a primary key, two rows whose key differs only
in that digit reach the destination with the same key, and a merge or upsert
keeps one of them. Non-Unicode text is decoded by its column's collation.

Well-known binary has no spatial reference ID. To keep it, add a computed
column such as `location.STSrid` to the table.

## Incremental reads

Incremental resources need a primary key without `sql_variant` columns and a
non-null cursor column, which is a `datetime`, `datetime2`, `smalldatetime`,
`datetimeoffset` or `rowversion` column. Conventional names such as
`updated_at` and `ModifiedDate` are recommended automatically, then a
`rowversion` column. A cursor can also be selected per pipeline resource.

The first incremental run captures the current `(cursor, primary key...)`
high watermark, then performs a resumable primary-key backfill. Later runs
read the rows after the watermark up to a high watermark taken when the run
starts.

A `rowversion` cursor is exact. The server advances it on every insert and
update, and a run never reads past `MIN_ACTIVE_ROWVERSION()` taken before its
read starts, so a transaction still open then cannot later commit below the
watermark. A `rowversion` cursor takes no lookback.

A timestamp cursor depends on the application to advance it on every change.
A transaction that commits after the high watermark was read, with an older
timestamp, is missed unless a lookback covers it. Configure a positive
per-resource lookback to re-read a recent window, and use incremental upsert
with it, since those rows are read again. An index beginning with the cursor
and followed by the primary key keeps incremental reads from sorting.

```sql
CREATE INDEX users_incremental ON dbo.users (updated_at, id);
```

## Permissions

The login needs `SELECT` on the tables it reads and permission to see their
metadata, which `SELECT` grants.
