The PostgreSQL source reads tables as resumable full snapshots, incremental
timestamp-cursor pulls, or logical-replication CDC. It picks a physical read
strategy per table rather than using one strategy for everything, and every
strategy checkpoints so an interrupted run resumes instead of restarting.
The connector is beta.

## Read strategies

`scan_strategy` controls how full snapshots read the heap. It is a physical
choice, deliberately separate from the pipeline's Full/Incremental/CDC mode.
Large tables split into parallel shards (heap pages divided by `shard_pages`,
capped at 64), and the chosen strategy and shard layout are frozen into the
checkpoint at plan time, so a resume never changes the plan mid-flight.

### keyset (default)

Walks the primary-key index in order (`WHERE (pk) > cursor ORDER BY pk LIMIT
page_size`), with the cursor carried in each record's key. Shard boundaries come from
integer arithmetic over `MIN`/`MAX` when the leading PK column is an integer,
or from equal-count sampled boundaries via `percentile_disc` for UUID, text,
and timestamp keys. The bottom and top shards are open-ended. Resumable to
the exact row.

### bitmap

Same shard boundaries as keyset, but each sub-range is read with a plain
range predicate (no `ORDER BY`, no `LIMIT`), leaving the planner free to
use a bitmap heap scan. That scan collects matching index TIDs, sorts them by
heap block, and reads in ascending physical order with prefetch. Better I/O
on heaps uncorrelated with the key, at the cost of coarse resume. Each
sub-range is all-or-nothing, and its rows are stamped `Coarse`.

### ctid

Selected only by an explicit `scan_strategy: ctid`. Divides the table into
physical block-range shards for fast sequential I/O, and parallel shards
share one exported snapshot. Each shard records run-start stamps (filenode,
`relfrozenxid`, xmin horizon, page count) and reconciles on resume. A
filenode mismatch (`VACUUM FULL`, `CLUSTER`, `TRUNCATE`) re-plans the whole
table. Horizon reconciliation re-delivers rows whose `xmin` is newer than the
run-start horizon on completed ranges, and if `relfrozenxid` advanced, the
rescan runs unfiltered. Blocks appended past the run-start size are delivered
unfiltered.

### auto

Probes `pg_stats.correlation` for the leading primary-key column, a measure
of how close the heap is to physical key order. `|correlation| >= 0.8` picks
keyset, and anything less picks bitmap. If statistics are missing, the router
runs `ANALYZE` once and retries. A still-missing statistic is treated as
random (bitmap). The probe never fails a run. Only this keyset-versus-bitmap
verdict is acted on today. The router's other modes are internal and not
reachable from `auto`.

## Incremental

Incremental mode requires a primary key and a `timestamp`/`timestamptz`
`NOT NULL` cursor column. Filament auto-ranks conventional names
(`updated_at`, `modified_at`, `last_modified_at`, `last_updated_at`,
`updated`, `modified`) and accepts an explicit per-resource override for
anything else. The application must advance the cursor on every insert and
update. Static IDs and random UUIDs are not valid watermarks.

The watermark is compound, `(cursor, pk...)`, so rows sharing a timestamp are
never skipped. Each cycle opens a repeatable-read transaction, captures the
high watermark at the snapshot, and pages `low < key <= high` ordered by
`(cursor, pk...)`. A default 300-second lookback rewinds the low bound to
absorb late commits and clock skew. The resulting duplicates are handled by
upsert.

The first run captures the high watermark, then performs a keyset backfill in
`incremental_backfill` mode. On completion it is promoted to steady-state
incremental, so changes committed during the backfill are replayed rather
than lost. Hard deletes are not observable through an update watermark. Use
CDC when deletes must be replicated.

## CDC

CDC streams `pgoutput` over a persistent logical replication slot. It
requires `wal_level=logical` and a primary key on every selected table. By
default the connector creates the publication and keeps its table list
current with `publish = 'insert, update, delete'`. Set
`manage_publication=false` when an administrator provisions it.

When a selected table has no CDC checkpoint, the slot is created with an
exported snapshot and the table is read in full through that snapshot, so the
baseline and the change stream share one consistent point. Run row limits do
not apply to this bootstrap read.

Steady-state runs are bounded catch-up cycles. Each replays from the oldest
resource LSN to `pg_current_wal_lsn()` at cycle start, then returns.
Continuous CDC is a re-request loop, so it can run on a schedule.
Zero-change runs still persist the final LSN per resource. A
primary-key-changing update is emitted as a delete of the old row plus an
insert of the new one. Standby status is reported every 10 seconds, and only
the previously durable cursor is acknowledged.

<Warning>
  CDC has operational sharp edges:

  - Replication slots are never dropped automatically. An abandoned pipeline's
    slot retains WAL indefinitely, so drop the slot when you retire a pipeline.
  - A "slot is active" error means another client holds the slot. Use a
    unique `slot_name` per pipeline.
  - A checkpoint older than the slot's confirmed position is a hard error.
    The WAL was consumed by another client, and the stream cannot be replayed.
  - `TRUNCATE` of a tracked table fails the run.
  - An update carrying an unchanged TOAST column with no old value is an
    error. Set `REPLICA IDENTITY FULL` on that table.
</Warning>

## Keyless tables

A table without a primary key is still readable in full. It falls back to the
ctid path with the ctid as the record id. That read is not resumable, so a
resume re-reads the whole table. Incremental and CDC both reject keyless
tables, since each requires a primary key.

See [Replication modes](/pages/guides/concepts/replication-modes) for how
modes map to write policies, and
[Integrity & checkpoints](/pages/guides/concepts/integrity-and-checkpoints)
for why plans are frozen at plan time.
