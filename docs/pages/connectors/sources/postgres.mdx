`connectors/postgres/source` implements resumable reads from a PostgreSQL
source, with a router that picks a physical read strategy per table rather
than using one strategy for everything.

## How it chooses a read strategy

At plan time — before the first row is read — the router asks Postgres one
question (`pg_stats.correlation` for the leading primary-key column: how
close is the heap to physical key order?) and combines it with a couple of
facts from the run config:

| Condition | Mode | What it means |
|---|---|---|
| CDC run with a logical slot available | `ModeSlot` | Streams committed row changes via WAL replay |
| Table declared append-only | `ModeCtidAppendOnly` | Physical block reads, no xmin bookkeeping needed |
| `\|correlation\| >= 0.8` | `ModeKeyset` | Heap is already near key order — walk the PK index in order |
| Primary key is mutable | `ModeCtidXmin` | Physical block reads plus a reconciliation pass for moved rows |
| Otherwise (random keys, immutable PK) | `ModeBitmap` | Bitmap heap scan — same correctness as keyset, better I/O pattern |

The chosen mode is frozen into the checkpoint at plan time and reused on
every resume of the same run, so the shard layout never changes mid-flight —
see [Integrity & checkpoints](/pages/guides/concepts/integrity-and-checkpoints) for why
that matters.

<Accordion title="What each mode actually does">
  **ModeKeyset** — issues `ORDER BY pk LIMIT` page queries, walking the PK
  index in order. Each page is one contiguous disk read when the heap is
  already correlated with the key. Resumable to the exact row.

  **ModeBitmap** — splits the key space into sub-ranges and reads each with
  a plain range predicate (no `ORDER BY`), letting Postgres collect matching
  index TIDs, sort by heap block, and read them in ascending order with
  prefetch. Resume is all-or-nothing per sub-range.

  **ModeCtidXmin** — divides the table into physical block-range shards
  (`ctid`) for fast sequential I/O, with three guards for safety across a
  resume boundary: a rewrite guard (VACUUM FULL / CLUSTER / TRUNCATE
  invalidates the cursor), horizon-compare reconciliation (re-scans for rows
  written or moved after run-start), and a freeze guard (falls back to an
  unfiltered rescan if `relfrozenxid` advanced past the horizon).

  **ModeCtidAppendOnly** — like `ModeCtidXmin` without the xmin apparatus,
  since rows never move or update.

  **ModeSlot** — a logical replication slot pins an LSN so updated or moved
  rows return via WAL replay; used for CDC.
</Accordion>

## Modes

Supports `ModeFull`, `ModeIncremental`, and `ModeCDC`. CDC uses the built-in
`pgoutput` plugin and bounded catch-up cycles, so it can run on a schedule. When
a selected table has no CDC checkpoint, Filament creates the replication slot
first, reads the table in full through the slot's exported snapshot, and retains
WAL from that snapshot's consistent point while the scan runs. It then replays
through a watermark captured after the scan, including changes committed during
the snapshot. After the sink commits, the run stores its WAL LSN on the stable
pipeline route. Later scheduled runs skip the snapshot and resume from that
per-resource LSN.

CDC requires `wal_level=logical`, a primary key on every selected table, and a
unique persistent `slot_name` per pipeline. By default the connector creates the
`filament` publication and adds selected tables; set
`manage_publication=false` when an administrator provisions it. Set `publication`
and `slot_name` explicitly when more than one CDC pipeline reads the database.

For tables with unchanged toasted columns, use `REPLICA IDENTITY FULL` so updates
carry enough old-row data to construct a complete change record. See
[Replication modes](/pages/guides/concepts/replication-modes).

## Incremental cursor selection

Incremental upserts use one watermark per table. Filament ranks conventional
columns (`updated_at`, `modified_at`, `last_modified_at`, `last_updated_at`,
`updated`, then `modified`) and the pipeline editor allows an override. Reads
are ordered and checkpointed by `(cursor_column, primary_key...)`, so rows that
share a timestamp are not skipped. The first run performs a bounded full
baseline using the normal primary-key shards; later runs inherit the last
acknowledged compound watermark. Filament captures that watermark before the
backfill, so the next run safely replays changes committed while shards were
running. A five-minute lookback rewinds timestamp cursors by default to absorb
late commits and clock skew; the resulting duplicates are handled by upsert.

Cursor overrides are limited to timestamp columns. For a non-conventional
timestamp, Filament requires an explicit selection because the application must
advance that value monotonically on every insert and update. Static IDs, random
UUIDs, and arbitrary text columns are not valid update watermarks.

Cursor fields must be `NOT NULL`; otherwise Filament cannot advance a reliable
watermark. Hard deletes are not observable through an update watermark; use
CDC, tombstones, or a soft-delete column when deletes must be replicated.
