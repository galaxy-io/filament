---
title: "Replication modes"
description: "Read modes, write modes, and the ingestion types they compile to"
---

Two levers set Filament's replication behavior. One is how a resource is
read (full, incremental, or CDC), the other how it is written (append,
replace, or upsert). The engine compiles each pair into an ingestion type that fixes the
sink mode, key requirements, atomicity, and checkpoint behavior.

## Replication mode is a connection property

A source connection is either **standard** or **CDC** (`ReplicationMode`,
resolved from the connection's config). Sources without CDC support are
always standard. Standard connections read with queries, while CDC
connections replicate from the database's change stream. The mode is
immutable. To switch, create a new connection.

Pipelines built on a CDC connection carry no read or write levers. The
change stream defines the read, and CDC compiles to a `merge` write of
ordered inserts, updates, and deletes.

## Read and write modes

Read mode is chosen per resource on standard connections:

| Read mode | Source behavior |
|---|---|
| `full` | Read every selected row on every run |
| `incremental` | Backfill once, then read rows past a durable cursor |

There are three write modes:

- `append`: keep every extracted row version
- `replace`: swap the destination for a fresh snapshot
- `upsert`: one current row per primary key

A `delete` write mode exists at the engine level (`incremental_delete`) but
is not user-selectable. When no write mode is chosen, full reads default to
replace and incremental reads to upsert.

Incremental cursors do not observe hard deletes — use CDC when deletions
must propagate.

## Compiled ingestion types

Each (read, write) pair compiles to an `IngestionType`. `full_replace` is
the default when nothing is specified.

| Ingestion type | Sink mode | Requires PK | Atomicity | Checkpoint |
|---|---|---|---|---|
| `full_replace` | replace | no | resource | none |
| `full_upsert` | upsert | yes | batch | after each batch |
| `full_append` | append | no | batch | none |
| `incremental_append` | append | no | batch | after each batch |
| `incremental_upsert` | upsert | yes | batch | after each batch |
| `cdc_append` | append | yes | batch | after commit |
| `cdc_merge` | merge | yes | batch | after commit |

`ResolveIngestionPlan` validates every ingestion type in the run:

- The connection's replication mode must match (CDC ingestion requires a CDC connection and vice versa)
- The source must advertise a matching `SourcePolicy`
- The sink must accept the write mode. Any sink can serve append and replace, and upsert falls back to the sink's `Upsertable` capability

Where a primary key is required, it resolves from the source's schema or
discovery. No key is an error.

## Per-resource model

Ingestion types are per resource. A run request carries an
`IngestionTypes` map from resource name to type, where the `""` entry is
the route default. Resources on one route may mix full and incremental
freely. The one route invariant is CDC purity. Any CDC entry makes the
whole run CDC, and CDC never mixes with other types on one route.

## Version policy

For upsert writes, the engine binds a `VersionPolicy` that tells the sink
which of two rows with the same key is newer:

- **`insert_order`**, for full reads (and sources without a usable cursor):
  the sink's insertion or merge semantics decide conflicts.
- **`cursor`**, for incremental reads: rows are ordered by the incremental
  cursor field.

The cursor field comes from the source's `CursorColumnProvider`. It is the
field configured in `ResourceCursorConfig` (which can also set a lookback
for sources that support it), or the connector's `Recommended` column when
none is configured. A configured column that does not exist, or one that is not
`Eligible`, fails plan resolution, as does having no recommended column
and no configuration.

This is distinct from the checkpoint. The checkpoint says where the next
read resumes, and the version policy says which already-written row wins. See
[Integrity & checkpoints](/pages/guides/concepts/integrity-and-checkpoints)
for how cursors are persisted.

## Row lineage columns

Filament reserves the `_filament_` column namespace and appends lineage to
every newly replicated row:

- `_filament_run_id`: the logical run that materialized the row
- `_filament_run_started_at`: that run's first start time in UTC

CDC rows also carry:

- `_filament_operation`: `insert`, `update`, or `delete`
- `_filament_source_position`: the source LSN, binlog position, or equivalent
- `_filament_sequence`: deterministic ordering within the change stream

The columns are nullable so existing destination tables can evolve without a
rewrite; rows written before the columns were introduced remain null. A source
schema that already uses a reserved name is rejected rather than overwritten.
