description: "How connections, tables, and sinks decide the way data moves."

How data moves is decided by three choices made at two different times.

## Replication mode

A connection replicates in one of two modes, chosen when the source connection
is created. Standard connections read with queries. CDC connections stream
changes from the database's log and need database side preparation, such as
logical replication on PostgreSQL. APIs are always standard, so they show no
choice at all.

Replication is a property of the connection. Pipelines built on a CDC
connection never ask how to read. There are no cursors to pick and no per
table options, because the change stream already carries every insert, update,
and delete in order.

## Incremental write versions

For an incremental upsert, Filament resolves the selected read cursor into a
per-resource `VersionPolicy` on the sink's `WritePolicy`. Sinks with
insert-based upsert semantics can use that source field to order competing
values for the same primary key. This is distinct from the durable checkpoint:
the checkpoint says where the next read resumes, while the version policy says
which already-written row is newer.

Snapshot upserts and sources that do not expose a safe row-level cursor use the
sink's insertion-order conflict semantics; Filament does not synthesize a
run-level version. A cursor is eligible for versioning only when it is present,
non-null, and advances whenever the source row changes.

<Tip>
  PostgreSQL is a good example of a source that picks its read strategy
  dynamically even within a single mode — see [Postgres
  source](/pages/connectors/sources/postgres) for how it chooses between keyset,
  bitmap, and ctid-based scans.
</Tip>

## Read mode

On a standard connection, each table chooses how it is read. Full rereads the
whole table every run. Incremental reads only rows past a cursor column and
needs one to exist. A table with a usable cursor column can go either way, and
a recommended column is detected automatically when the user does not pick
one. A table without one must be read in full.

## Write mode

Each sink declares how it can land records. Append keeps the history of every
load. Replace and upsert keep the current state, with upsert available only on
sinks that support merging by key and requiring a primary key on the table.

## Derivation

The server compiles these choices into an internal ingestion type stored on
each pipeline edge. Users never select it. A per resource edge carries its own
read and write mode, which is how one pipeline mixes fully replicated tables
with incremental ones. Validation answers with the same vocabulary the user
chose from, reporting per table which read modes are possible, which cursor
columns qualify, and what would fail at run time.
