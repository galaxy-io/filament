Filament exposes two replication modes at connection creation. Standard
pipelines then choose how each resource is read and how each destination route
is written.

## Replication mode

A source connection is either **Standard** or **CDC**. Standard connections
read with queries. CDC connections stream changes from a database log and may
need database-side preparation, such as logical replication on PostgreSQL.
Sources without CDC support are always Standard.

Replication is a property of the connection. Pipelines built on a CDC
connection have no editable read or write mode and no cursor. The change stream already
defines the read and applies ordered inserts, updates, and deletes.

The replication mode is immutable. Create a new connection when changing
between Standard and CDC so existing pipeline versions cannot silently change
meaning.

## Standard read and write modes

Read mode is selected per resource. Write mode is selected once per destination
route and applies to every resource sent from that source to that destination.

| Read mode | Source behavior |
|---|---|
| **Full** | Read every selected row on every run |
| **Incremental** | Backfill once, then read rows after a cursor |

| Write mode | Destination behavior |
|---|---|
| **Append** | Preserve every row version Filament extracts |
| **Replace** | Replace the destination with a full snapshot |
| **Upsert** | Insert or update one current row per primary key |

Full + Replace is the default. Filament does not automatically choose Incremental
just because a cursor-like column exists: Incremental changes delete semantics
and requires an explicit choice.

Incremental requires a usable cursor column. Upsert requires a primary key and
a sink that can merge by key. A recommended cursor is selected automatically
when one is safe; otherwise the pipeline editor asks for it. Update cursors do
not observe hard deletes—use CDC, tombstones, or soft deletes when deletions
must propagate.

The valid combinations are Full + Append, Full + Replace, Full + Upsert,
Incremental + Append, and Incremental + Upsert. Replace requires a Full read.
The server validates the actual source, resource, and sink combination and
returns supported read modes per resource and supported write modes per route.

## Incremental write versions

For an incremental upsert, Filament resolves the selected read cursor into a
per-resource `VersionPolicy` on the sink's `WritePolicy`. Sinks with
insert-based upsert semantics can use that source field to order competing
values for the same primary key. This is distinct from the durable checkpoint:
the checkpoint says where the next read resumes, while the version policy says
which already-written row is newer.

Snapshot upserts and sources that do not expose a safe row-level cursor use the
sink's insertion-order conflict semantics; Filament does not synthesize a
run-level version. A cursor is eligible for versioning only when it is present,
non-null, and advances whenever the source row changes.

<Tip>
  PostgreSQL is a good example of a source that picks its read strategy
  dynamically even within a single mode — see [Postgres
  source](/pages/connectors/sources/postgres) for how it chooses between keyset,
  bitmap, and ctid-based scans.
</Tip>

## Engine behavior

A pipeline edge stores its resource read mode, route write mode, and optional
per-resource cursor overrides. All edges on a route carry the same write mode.
For CDC, an edge stores neither lever. The server compiles that intent
into source read policy, sink write policy, operation handling, and checkpoint
behavior. Those mechanisms remain internal so every client sees the same small
model without losing an explicit description of the result.
