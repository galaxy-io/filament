Two guarantees run through every Filament pipeline. What the sink wrote is
verified against what the source produced, and progress is persisted so
eligible runs resume instead of starting over.

## Integrity checking

Verification is a CRC32-C (Castagnoli) checksum, not row counts. Each
record is hashed over a canonical encoding:

```
{"id":<json-escaped id>,"op":<decimal>,"data":<payload verbatim>}
```

with a length prefix per record, so regrouping or reordering records
changes the result. The encoding is a deterministic, injective hash
preimage. It is deliberately not guaranteed to be valid JSON.

Both sides compute the checksum independently. The pipeline's writer
computes the read-side CRC over the batch immediately before calling
`Sink.Apply`. The sink computes the write-side CRC over what it actually
staged or wrote and returns it in `WriteReceipt.WriteCRC`.

After `Apply` returns, the writer compares the two. A match publishes
`batch.written` and `batch.integrity_verified`. A mismatch publishes
`batch.chunk_divergence` and fails the run fatally. A divergent batch is
never silently accepted.

## Checkpoints

Two durable stores hold progress:

- **Run-scoped**: within-run resume for checkpointing full reads. A
  restarted run reloads its own shard plan and cursors.
- **Cross-run**: durable incremental and CDC progress, keyed by
  `{PipelineID, PipelineVersionID, Route, Resource}` and shared by every
  run of one immutable pipeline route. An incremental resource without a
  versioned pipeline route fails.

Checkpoint data comes in these cursor modes:

- `keyset`: ordered key ranges split into shards
- `bitmap`: ack-counted coarse reads
- `ctid`: physical scan position
- `incremental`: ordered watermark with a full primary-key tie-breaker
- `incremental_backfill`: a resumable sharded initial snapshot that promotes
  to its captured start watermark on completion
- `stream`: a single monotonic replication-log position such as an LSN or
  binlog offset

### Seeding and advancement

The runner seeds checkpoints before extraction — the one place a run writes
durable state itself. Each resource shape loads its own prior progress:

- Incremental resources load prior cross-run checkpoints and plan from them
- Checkpointed full reads load run-scoped state
- CDC loads per-resource stream positions

Advancement is folded from facts:

- The batcher stamps each flushed batch with a cursor delta
- The writer carries it on `batch.written` (a sink may override via
  `WriteReceipt.Checkpoint`)
- The tracker (the only writer of fact-derived state) folds deltas and
  persists every `CheckpointEvery` written batches (default 25), flushing
  immediately on `resource.completed` and at run termination

### Commit gating

Incremental and CDC cursors are tentative until the sink commits. Cross-run
checkpoint state persists only after `Sink.Commit` succeeds and the run
completes. A run that fails before commit leaves the durable cursor where
the last successful run left it, so the next run re-reads rather than
skipping data.

Which runs can use this progress to resume, and what happens on failure, is
covered in [Runs and recovery](/pages/guides/concepts/runs-and-recovery).
