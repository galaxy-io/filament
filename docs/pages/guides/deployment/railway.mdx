Filament publishes a Railway template that deploys the server, control plane,
worker, PostgreSQL, and NATS as one connected project:

<a href="https://railway.com/deploy/filament?referralCode=H5DcHR&amp;utm_medium=integration&amp;utm_source=template&amp;utm_campaign=generic">
  <img src="https://railway.com/button.svg" alt="Deploy on Railway" />
</a>

## What gets deployed

| Resource | Purpose |
|---|---|
| Filament server | Serves the API and web application over Railway's public network |
| Filament control plane | Fires schedules and tracks pipeline runs |
| Filament worker | Links the connectors, serves the catalog, and executes pipeline runs |
| PostgreSQL | Stores pipelines, runs, checkpoints, schedules, and encrypted credentials |
| NATS | Carries lifecycle events through JetStream |

The template connects the services over Railway's private network and supplies
the shared PostgreSQL DSN, NATS URL, worker URL, and encryption key. Database
migrations run before the server starts.

## Deploy the template

<Steps>
  <Step title="Open the template">
    Click **Deploy on Railway** above, sign in, and choose the workspace where
    you want to create the project.
  </Step>
  <Step title="Review the project">
    Confirm that the server, control plane, worker, PostgreSQL, and NATS
    services are included. Review the resource plans and generated variables before
    deploying.
  </Step>
  <Step title="Wait for the services">
    Railway provisions the backing services, applies database migrations, and
    starts the server, control plane, and worker. Wait for every service to
    become healthy.
  </Step>
  <Step title="Open Filament">
    Open the public domain for the Filament server. If the template has not
    created one, select the server service and generate a domain under
    **Settings → Networking**.
  </Step>
</Steps>

## Connectors and run execution

The worker is the only service that links connector drivers. It runs with
`-serve -execute`. With `-serve` it answers connector calls from the server and
control plane, which reach it through `WORKER_URL` on the private network. With
`-execute` it consumes requested runs from NATS and executes them itself, since
Railway has no Kubernetes Jobs API. The control plane sets
`DISPATCH_MODE=worker` and dispatches nothing. Every pipeline run shares the
worker service's CPU and memory.

<Warning>
Keep the control plane at one replica. Multiple replicas may race while
coordinating schedules and pipeline runs.
</Warning>

Increase the worker service's CPU and memory for concurrent or
resource-intensive pipelines. Use the
[Kubernetes deployment](/pages/guides/deployment/kubernetes) when runs need
isolated containers or independent resource configuration.

## Before production

- Configure authentication before storing sensitive connector credentials on
  a public deployment. Authentication is disabled when `AUTH_PROVIDER` is
  unset.
- Keep `ENCRYPTION_KEY` backed up and unchanged. Replacing it makes existing
  encrypted credentials unreadable.
- Configure retention and backups for PostgreSQL and JetStream to match your
  recovery requirements.
- The template tracks the `latest` image tag for the server, control plane,
  and worker. Pin all three to the same Filament release before relying on
  the deployment, and upgrade them together.

See [Configuration](/pages/guides/deployment/configuration) for authentication,
secrets, logging, and other runtime settings.
