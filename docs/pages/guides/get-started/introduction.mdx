Filament is a CDC and replication engine written in Go. It:

- Moves data from sources to sinks with full, incremental, and CDC replication
- Verifies every batch with a CRC32-C checksum computed independently on the read and write side
- Runs as a single binary or embedded in your own Go process as a library

Connectors, the data store, and the event bus are interfaces with
swappable implementations.

Runs that carry resumable progress (incremental and checkpointed full reads)
pick up from their last durable checkpoint instead of starting over. Which run
shapes qualify, and how resume works, is covered in
[Runs and recovery](/pages/guides/concepts/runs-and-recovery).

## How it's put together

Filament's core is one code path, the runner, which executes a run from
extraction through verified write. Everything around it (API server, control
plane, dispatch) decides *where* that code path executes, never *how*.

The `server` / `control-plane` / `worker` split you'll see in the deployment
docs is one deployment shape, built for Kubernetes:

- The server owns connections, pipelines, and run requests
- The control plane schedules and dispatches
- Each run executes as its own worker Job

But dispatch is pluggable. The same runs execute in-process inside the
control plane, inside the standalone binary, or inside your own process when
you embed Filament as a library. State lives in a data store (Postgres in
production) and progress flows over an event bus (NATS JetStream) — those
two are the only surfaces the processes share.

Read [Architecture](/pages/guides/concepts/architecture) for how the modules,
the pipeline, and the fact-driven state model fit together.
