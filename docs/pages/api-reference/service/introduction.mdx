Filament's API is [ConnectRPC](https://connectrpc.com), generated from the
protobuf definitions in `protos/ingestion/v1/`, `protos/metrics/v1/`, and
`protos/auth/v1/`.
`ingestion.v1.IngestionService` (connectors, connections, pipelines, runs) and
`metrics.v1.MetricsService` (dashboard aggregations) share one listener with
`auth.v1.AuthService` (authentication and team management). The built-in web
app and Python SDK use this same API.

Every RPC has a Connect HTTP POST route at `/{package.Service}/{Method}`:

```
POST /ingestion.v1.IngestionService/CreatePipeline
POST /metrics.v1.MetricsService/QueryTimeseries
```

The `server` binary serves these services on `SERVER_ADDR` (default `:8080`).
The `standalone` binary and the embeddable `app.Run` library serve the same API
on `INGESTION_ADDR` (default `:8080`).

## Protocols

The servers listen for HTTP/1.1 in plaintext. That determines which of the
three ConnectRPC wire protocols work against a default deployment.

| Protocol | Works out of the box |
|---|---|
| Connect (JSON or binary) | Yes (plain HTTP/1.1 POST) |
| gRPC-Web | Yes (HTTP/1.1) |
| gRPC | No (needs HTTP/2) |

Plain gRPC needs HTTP/2 end to end. The shipped binaries listen plaintext
without h2c, so a stock gRPC client fails against them directly. Serving
native gRPC requires enabling HTTP/2 on the backend listener as well as on
any proxy in front of it. TLS termination at a proxy alone does not enable
HTTP/2 on the backend. Connect and gRPC-Web clients need nothing extra.

The Connect protocol is ordinary JSON over POST, so any HTTP client works:

```sh
curl -X POST http://localhost:8080/ingestion.v1.IngestionService/ListConnectors \
  -H "Content-Type: application/json" \
  -H "Connect-Protocol-Version: 1" \
  -d '{"kind": "CONNECTOR_KIND_SOURCE"}'
```

For authenticated deployments, also send `Authorization: Bearer <token>`.

## OpenAPI

Run `buf generate` (or `just proto`) from the repository root to regenerate
the Go bindings and `api/openapi.json`. The pinned
[protoc-gen-connect-openapi](https://github.com/sudorandom/protoc-gen-connect-openapi)
plugin in `buf.gen.yaml` exports OpenAPI 3.1 for the existing unary Connect
JSON endpoints. Buf runs this plugin remotely; generation requires network
access to the Buf Schema Registry.

The specification describes request and response types, Connect headers,
and error responses. Fern uses it to generate the Python SDK, with method
names and authentication metadata configured in `fern/`. The SDK calls the
existing Connect JSON endpoints directly.

Run `just sdks` from the repository root to regenerate the OpenAPI
specification and configured SDKs. This requires Buf and Fern login.
Use `just proto-check` to check generated API files against their committed
versions.

## Python SDK

Install [filament-py from PyPI](https://pypi.org/project/filament-py/).
The SDK requires Python 3.10 or newer:

```sh
uv add filament-py
```

For an existing virtual environment, use `uv pip install filament-py`.

```python
from filament import Filament

filament = Filament(base_url="http://localhost:8080")

for connector in filament.connector.list().connectors or []:
    print(connector.name)

pipeline = filament.pipeline.create(name="daily-import").pipeline
```

Pass `token="your-access-token"` to `Filament` when authentication is enabled.
Use `AsyncFilament` for async applications. The client creates its HTTP client
and supplies the Connect protocol header automatically.

`pipeline.create(...)` creates metadata. Before the first run, save a graph
with `pipeline.version.create(...)`, then call `pipeline.run(...)`.
The [Python SDK README](https://github.com/galaxy-io/filament/blob/main/sdks/python/README.md)
includes a complete example that creates source and sink connections,
discovers resources, saves a graph, and runs the pipeline.

The SDK and OpenAPI specification cover unary methods. Streaming `TailRun`
requires a client with Connect streaming support and is not included.

## Authentication

When an identity provider is configured, the API accepts its bearer tokens
or Filament's session cookie. Only the auth configuration, login, logout,
registration, and invitation acceptance procedures are public.

Without an identity provider, the API is unauthenticated. Keep such
deployments private or protect them at the network layer.

## Tenancy

Authenticated requests use the tenant resolved from the caller's identity.
With authentication disabled, every request uses the server's configured
default tenant. Request bodies and query parameters do not select a tenant.

## Errors

Failures are standard [Connect error codes](https://connectrpc.com/docs/protocol#error-codes).
These are the codes you will actually see.

| Code | When |
|---|---|
| `invalid_argument` | Malformed request |
| `unauthenticated` | Missing, invalid, or expired credentials when authentication is enabled |
| `permission_denied` | The caller lacks the required role |
| `not_found` | No row for the id, or an unknown connector name on `GetConnector` |
| `failed_precondition` | The operation is valid but the state refuses it |
| `aborted` | Optimistic-lock conflict on `version` |
| `already_exists` | `CreatePipelineSchedule` on a pipeline that already has one |
| `unimplemented` | The RPC or feature is unavailable in this deployment |

Some specifics worth knowing:

- `invalid_argument` covers missing required fields, an invalid graph on
  `CreatePipelineVersion`, a bad cron expression, and an undecodable
  pagination cursor.
- `failed_precondition` covers deleting a connection a pipeline still
  references, updating a deleted connection, a secret that fails to resolve,
  and `TailRun` without an event bus.
- `aborted` means the `version` on an update no longer matches the stored
  row. Re-read and retry.
- `unimplemented` covers `MetricsService` without a metrics store and
  discovery or column RPCs on connectors that don't support them.

Validation of connector configs is the exception. `ValidateConfig` and
`ValidatePipeline` return validation problems in their response bodies rather
than as RPC errors, so a form can display every failure together.

## Pagination

List RPCs take an optional `PaginationRequest`.

| Field | Behavior |
|---|---|
| `page_size` | Default 25 when unset. Values above 1000 are clamped to 1000 |
| `cursor` | Opaque token from a previous response. Do not construct one |

The response's `PaginationResponse` carries `total` plus `previous_cursor` and
`next_cursor` when more pages exist in that direction. Omitting `pagination`
entirely returns every row, which is convenient for scripts but expensive on
large tables.

## Health

Three plain HTTP endpoints sit beside the RPC routes on the same listener:

- `GET /livez`: always 200 while the process is up
- `GET /startupz`: 200 once dependencies are connected and modules are mounted
- `GET /readyz`: 200 after startup while Postgres and NATS/JetStream answer; the
  server also ensures the default tenant exists

The control plane serves the same endpoints on `HEALTH_ADDR` (default `:8081`).
